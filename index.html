The harness

The projects run on a team of specialised AI agents, not a single general-purpose assistant. Each agent has a defined scope, operating model, and trust level. Most of the coordination happens between agents directly — including to external AI systems — without a human in the relay.

Rufus Orchestrator · DevOps

Executive assistant and main coordinator. Routes work to specialists, owns all production infrastructure, manages deployments, and maintains continuity across sessions via a persistent memory system.

Heimdal Market intelligence

Daily ingestion of investment signals from curated financial accounts on X. Scores, deduplicates, and routes signals for review.

Munin Research router

Processes bookmarks and research inputs. Classifies, routes, and drafts decision records when external content warrants a response.

Týr Portfolio analyst

Portfolio analysis, signal synthesis, and thesis validation. Consumes Heimdal's signals and the rebalancing engine's live output. Execution requires explicit approval.

Vidar Technical reviewer

Reviews plans, specs, and product documents for technical soundness and strategic alignment. Read-only — no external actions.

AntiGravity External · Development

Google's AI development tool. Owns the main branch of the rebalancing engine — feature development, architecture, tests. Coordinates with Rufus entirely through GitHub primitives.

Internal agents follow Norse mythology — names chosen to point toward what each agent should become, not just what it does today. External agents integrate through structured interfaces, not shared infrastructure.

Case study

Two AI systems, one codebase

The rebalancing engine is where the agent coordination is most concrete. Google's AntiGravity develops the software. Rufus operates it in production. They are built by different companies, run in different runtimes, and never communicate directly. Their shared interface is GitHub.

AntiGravity

Rufus

GitHub as the coordination layer

The two systems coordinate entirely through standard GitHub primitives — no shared API, no message queue, no real-time channel. GitHub is a natural interoperability standard for this: both systems know how to read and write Issues and PRs, and the label system provides just enough structure to make messages typed without requiring anything custom.

AntiGravity → Rufus
Issue · label: release-ready

"This version of main is production-ready. Here's what changed and what new config it needs." Rufus picks this up, verifies on the ops environment, and deploys to production at own discretion.

Rufus → AntiGravity
Issue · label: deployment-feedback

"The deployed ref is broken — here's the symptom, the logs, and the context." AntiGravity reads it on the next run and fixes accordingly. No human needs to be in the loop.

AntiGravity → Rufus
Pull request · feature → main

Standard development PRs with structured descriptions. Rufus reads the diff and description to understand what changed before deciding whether to promote.

Rufus → AntiGravity
Pull request · ops → main

When Rufus makes an infrastructure or operational change on the ops branch that's worth folding into the codebase proper, a PR goes up for AntiGravity to review.

The deployment cycle

Happy path

AntiGravity pushes code to main; opens release-ready Issue when ready
↓
Rufus pulls main to ops branch; runs on staging at ops.rebalancing.accordant.eu
↓
Rufus triggers workflow_dispatch deploy to rebalancing.accordant.eu
↓
Týr consumes live portfolio data from the running system for investment analysis

Failure path

Rufus detects health failure post-deploy
↓
Rufus opens deployment-feedback Issue with ref, symptom, and logs
↓
AntiGravity reads issue, investigates, pushes a fix to main
↓
AntiGravity opens new release-ready Issue; cycle repeats

The full audit trail lives in the GitHub Actions log and the repo's Issue history. Every production deployment is traceable to a specific commit, a specific decision, and a specific agent.

Philosophy

The approach

Whether AI systems can coordinate well enough to run something end to end — and what that looks like at small scale, without purpose-built tooling — is the actual question.

The rebalancing engine is one answer. The coordination layer doesn't need to be AI-specific: GitHub Issues and PRs work as a natural async protocol between agents from entirely different stacks. A label is a message type. An Issue is a structured async message. A PR is a change proposal with full provenance. Both systems already know how to use these primitives — nothing custom needed.

The consistent pattern across all projects: deterministic, auditable logic at the core, with AI as the reasoning and operating layer above it. Not AI generating code that humans maintain — AI as an ongoing operator of systems that remain legible and verifiable. Finance and tax are the starting point because the rules are codified, the stakes are concrete, and you know immediately whether the output is any good.
